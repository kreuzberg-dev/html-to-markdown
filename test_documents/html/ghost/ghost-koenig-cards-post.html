Why We Moved Our Build Cache to a Local Cluster

Cloud egress fees quietly became our third-largest infra line item. Here's what replaced it.

Dana Kowalski 10 August 2026

Our CI cluster was pulling the same layers from a cloud registry hundreds of times a day. Egress alone ran close to $4,000 a month before we did anything about it. This is the walkthrough of what replaced it.

The Numbers

Three months of billing data made the case for us on its own, without any need to argue about it in a meeting.

💡
A local pull-through cache doesn't need to be highly available — a cache miss just falls back to the origin registry, so a single node is fine to start.

The Setup

We run a single bare-metal box in the office closet as a pull-through cache for our container registry:

const cache = createRegistryMirror({
  upstream: "registry-1.docker.io",
  storagePath: "/mnt/cache",
  maxSizeGb: 500,
  evictionPolicy: "lru",
});

cache.on("miss", (ref) => {
  metrics.increment("cache.miss", { ref });
});

What We'd Do Differently

  • Provision the cache disk larger than you think you need — we resized twice in the first month
  • Put the cache behind the same VPN as CI runners, not the public office network
  • Monitor cache disk usage, not just hit rate — eviction silently degrades hit rate before you notice

Egress fees are a tax on not owning your own disks.

The Rack, Two Months In

We eventually split the single box into three cache nodes behind a round-robin DNS entry, mostly so a disk failure wouldn't take the whole cache offline mid-build. The photos below are from that upgrade.

⚠️
Round-robin DNS does not detect a dead node. We layer a health check in front of it now after one node silently served stale cache entries for two days.

Results

Egress cost dropped from roughly $4,000/month to under $300/month, and median CI job time for cache-heavy pipelines fell by about 40%. The office electricity bill went up by a number small enough that nobody has bothered to isolate it on a separate circuit yet.

Open Questions

We haven't solved cache warming yet — a cold node after a reboot still has to pull everything from upstream once before hit rate recovers. A couple of things we're considering for the next iteration:

  1. Periodically syncing the cache directory between nodes so a fresh node inherits a warm working set
  2. Pinning the most frequently used base images so they survive LRU eviction regardless of recency
  3. Moving from a single shared volume to per-node local NVMe, trading some duplication for lower latency
✅
If your CI egress bill is a rounding error, none of this is worth the operational overhead. It only paid off once our monthly pull volume crossed a few terabytes.
